# RE:FOCUS 心流交叉验证与落地方案

> **方案演进说明。** 本文保留了摇杆、RGB 和其他模块的早期候选设计；最终比赛 Demo 不使用摇杆，实际硬件以根目录 README 为准。

> 本文给出比赛 MVP 的工程判定标准。系统输出“高概率进入心流”，不把摄像头或电脑行为包装成心理诊断。

## 1. 结论

心流不能由“眼睛一直看屏幕”单独证明。RE:FOCUS 使用四路独立证据交叉验证：

1. **目标证据**：用户此刻要完成什么。
2. **人体证据**：是否在席、是否大体朝向工作区域、是否发生明显中断。
3. **电脑证据**：是否持续停留在与目标相关的任务窗口。
4. **成果证据**：文档、代码、设计或研究是否出现真实进展。

目标证据是前提，电脑证据和成果证据权重最高；人体状态只作辅助，避免把思考、残障、ADHD 或个人动作习惯误判为不专注。

## 2. C 板落地选择

队伍已经领取 C 板（ESP32-S3 AIoT 全功能套件），不再保留 A/D 板实施路线。C 板的优势是 PIR、激光测距、六轴、摄像头、按键和多种输出可以为“人在不在、是否回来、用户是否确认恢复”提供独立物理证据。

比赛 MVP 采用**传感器优先模式**：

- 电脑摄像头：本地检测在席、头部是否大体朝向工作区；不做人脸身份识别。
- C 板 PIR + VL53L0X：辅助验证人在席、离席和回来；具体 I2C 引脚先真机确认。
- C 板摇杆/按键：声明开始、结束 Session 或确认回来。
- C 板 LCD/OLED + GPIO48 WS2812：显示热身、专注、已中断和恢复状态。
- 扬声器/麦克风：只在主闭环稳定后加入。

现成 Agent_link 的 `gc2145-camera` 只覆盖 GC2145、ST7789、快照和 WS2812。由于摄像头占用 GPIO4–18 中的大量引脚，并与 PIR、摇杆、编码器、DHT11、光照等默认示例接法冲突，摄像头优先模式单独验证，不直接与全部传感器并行承诺。详细引脚见 `hardware-c-board.md`。

## 3. 采样窗口

- 电脑事件：每 2 秒采样一次前台窗口；保存结构化标题/应用，不保存键盘内容。
- 人体状态：每 2 秒得到一次 `present`、`facing_workspace`、`large_motion`；原始画面默认不落盘、不上传。
- 成果变化：每 30 秒检查一次保存、文件差异、运行/测试、笔记或任务事件。
- 判定：每 60 秒计算一次最近 5 分钟滚动窗口。

## 4. 硬门槛

最近 5 分钟必须同时满足：

```text
已有明确 goal_id
人在席比例 >= 90%
朝向工作区域比例 >= 70%
目标相关窗口时间 >= 80%
无关窗口累计时间 <= 30 秒
无关窗口切换 <= 1 次
至少 1 个有效成果进展事件
没有离席 >= 30 秒
没有强中断 >= 60 秒
```

任一硬门槛不满足，不宣布进入心流，只保留“热身中”或“专注中”的普通状态。

## 5. 每项的可执行定义

### 人在席

- 5 分钟内检测到人脸或上半身至少 270 秒，记为通过。
- 连续 15 秒不在画面，记一次短暂离席。
- 连续 30 秒不在画面，立即产生 `flow_interrupted`。

### 朝向工作区域

- 头部大致朝向主屏幕至少 210 秒，记为通过。
- 单次偏离 15 秒以内视为正常思考。
- 连续偏离 30 秒降低置信度；连续 60 秒产生中断候选。
- 不要求持续眼球追踪；低清摄像头优先使用头部朝向。

### 任务窗口一致性

先由用户声明目标，Agent/规则把窗口分为 `relevant`、`neutral`、`unrelated`。

- VS Code → 终端 → 技术文档可以属于同一任务链，不算切换。
- 最近 5 分钟 `relevant + neutral` 占比至少 80%。
- 无关窗口单次不超过 20 秒、累计不超过 30 秒、次数不超过 1 次。
- 无关窗口连续 60 秒，立即产生中断。

窗口分类先用白名单和项目名做确定性判断，Agent 只处理无法确定的标题，避免每两秒调用模型。

### 有效成果进展

至少命中一项：

| 模式 | 有效进展事件 |
| --- | --- |
| 编码 | 文件保存且 diff 改变；运行、编译或测试产生新结果 |
| 写作 | 文档字符/结构发生变化并保存；新增批注或完成段落 |
| 设计 | 图层、组件、属性、画布或版本发生变化 |
| 阅读 | 页面推进并产生笔记、标记、摘录或问题 |
| 分析 | 查询、公式、筛选、图表或结果发生变化 |

只有鼠标移动或键盘敲击不算成果进展。阅读模式由用户在 Session 开始时选择，以免长时间阅读被误判。

### 稳定性与“躁动”

- 5 分钟内大幅姿态重置不超过 3 次：稳定。
- 4–5 次：只降低置信度，不直接中断。
- 超过 5 次且同时出现无关窗口或无成果：记为分心候选。
- 抖腿、转笔、小幅晃动不扣分。

## 6. 评分

硬门槛通过后再计算置信分：

| 证据 | 权重 |
| --- | ---: |
| 任务窗口与目标一致 | 25 |
| 真实成果进展 | 25 |
| 连续投入、低无关切换 | 20 |
| 人在席与朝向 | 15 |
| 个人操作节奏稳定 | 10 |
| 身体状态稳定 | 5 |

```text
score >= 75 且硬门槛全部通过
连续两个 5 分钟滚动窗口成立
=> high_probability_flow_entered
```

连续保持 10 分钟标记 `stable_flow`。低于 60 分连续 2 分钟标记 `flow_weakened`；出现离席 30 秒或无关窗口 60 秒，无需等待分数，直接标记 `flow_interrupted`。

## 7. “新心流”与“恢复心流”

### 新心流

同时满足：

- `goal_id` 改变，或新任务与旧任务语义明显不同；
- 新任务窗口占比达到 80%；
- 新任务产生至少一个成果进展；
- 新任务连续两个滚动窗口达到 75 分。

### 恢复心流

中断后仍回到相同 `goal_id`，重新打开原项目/文档并在 5 分钟内产生进展，标记 `flow_recovered`，不计作新心流。这是 RE:FOCUS 的核心价值。

## 8. 状态机与硬件反馈

```text
IDLE
→ WARMING_UP
→ LIKELY_FLOW
→ STABLE_FLOW
→ INTERRUPTED
→ RECOVERING
→ LIKELY_FLOW
```

建议反馈：

- `WARMING_UP`：柔和呼吸灯，屏幕显示目标。
- `LIKELY_FLOW/STABLE_FLOW`：灯光变暗，设备保持安静，进入“勿扰保护”。
- `INTERRUPTED`：自动生成 Checkpoint，不立刻训斥或震动。
- `RECOVERING`：用户回来按键后，屏幕/语音给出“做到哪里 + 下一步”。

## 9. 系统落地

```text
C 板 PIR/测距/按键
        ↓ BLE/串口（结构化事件）
电脑 Bridge + 电脑摄像头本地视觉
        + 前台窗口观察器
        + 文件/应用进展适配器
        ↓
本地规则引擎（实时评分与状态机）
        ↓ 只在关键节点调用
TiDB Agent Stack（窗口语义分类、Checkpoint、恢复表达）
        ↓
TiDB 保存 Session / Event / Checkpoint / Score
        ↓
C 板 LCD/OLED / WS2812（声音后置）
```

实时判定必须由本地规则完成，不能每两秒请求大模型。Agent 负责语义分类、总结和恢复建议；硬件动作由白名单程序执行。

## 10. 最小数据结构

```json
{
  "session_id": "...",
  "goal_id": "...",
  "timestamp": "...",
  "present": true,
  "facing_workspace": true,
  "foreground_app": "VS Code",
  "window_class": "relevant",
  "progress_event": "file_saved_with_diff",
  "large_motion": false,
  "flow_score": 82,
  "flow_state": "likely_flow"
}
```

只保存结构化事件；窗口标题在进入云端前做脱敏，摄像头原图默认不保存。

## 11. 比赛验收方法

用同一脚本连续演示三次：

1. 用户说出目标并开始 Session。
2. 在相关窗口内工作并产生真实文件变化。
3. 仪表盘展示四路信号和分数逐步达标。
4. 设备进入安静的心流保护状态。
5. 用户离席 30 秒，系统自动保存 Checkpoint。
6. 用户回来按键，设备说出原进度和下一步。

验收标准：三次均能产生正确状态事件、可核对的成果变化、Agent Checkpoint 和真实硬件输出；任何一次都不依赖人工后台改状态。

## 12. 降级路径

- C 板传感器链路不稳：电脑摄像头本地判断；C 板至少保留一个真实按键输入和 GPIO48 RGB 物理输出。
- C 板摄像头与传感器冲突：比赛 MVP 采用传感器优先模式；摄像头独立演示或通过验证后的重映射接入。
- 精确视线不稳：只用在席与头部朝向，降低人体信号权重。
- Agent Stack 暂不可用：本地模板生成 Checkpoint，恢复后补写 TiDB。
- ASR 不稳：按钮开始 + 网页文字目标；硬件仍参与完整闭环。
- 自动成果识别不稳：使用 VS Code 文件保存/diff 或指定文档保存事件作为比赛白名单。
