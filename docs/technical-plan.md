# 技术实施基线

## 先做垂直切片

两套方案共用同一验证顺序：

1. **设备 Hello World**：编译、烧录、串口、真实输入和真实输出。
2. **Agent Stack Hello World**：Project → Agent → Session → Turn → NDJSON 终止事件。
3. **Bridge**：真实设备事件转换成文本/结构化 Turn，Agent 结果转换成白名单设备命令。
4. **单一魔法瞬间**：只实现一条连续闭环。
5. **记录证据**：脱敏日志、Trace、屏幕录制、真实设备视频。
6. **增强功能**：只在主链路稳定后增加。

## 建议的中间协议

Agent 不应直接输出自由文本控制硬件。Bridge 接受一个小型白名单协议，例如：

```json
{
  "device_action": "show_state",
  "state": "thinking",
  "text": "正在生成离席摘要"
}
```

允许的动作只包括当前 Demo 所需的显示、灯光、音频或震动，并限制长度、颜色、时长和频率。

## AI Game Master 架构

```text
玩家手机（座位、私密动作、带身份语音）
             \                         
桌面 A 板（公共按钮/摄像头/声音/灯光）
              → Realtime Game Service
              → 确定性规则引擎
              → TiDB 游戏事件与权限视图
              → Agent Stack（摘要、补课、个人复盘）
              → 公共输出回 A 板，私密输出回个人手机
```

事件模型至少包含：game、player、seat、role、phase、event、visibility_scope、speaker、vote、absence_window。所有摘要必须先按 `visibility_scope` 过滤，再交给 Agent 生成自然语言。

保底：如果实时 ASR 不稳定，玩家按住自己的手机发言，或在 Demo 中用已标识的文本/短语输入；桌面硬件仍负责真实主持输出。

## RE:FOCUS 架构

```text
电脑端观察器（当前应用/网页、空闲、在席）
        → 本地结构化事件
        → Focus Service / TiDB
        → Agent Stack（相关性、Checkpoint、下一步）
        → Bridge
        → C 板灯光/屏幕（音频后置）
```

第一版不要持续上传屏幕或摄像头。优先发送：应用名、页面标题、是否在席、用户声明目标、手动保存点。原始图像仅在用户明确启用且确有必要时处理。

保底：如果自动观察不稳定，用一个浏览器扩展读取当前标签页，并用“离开/回来”按钮模拟在席事件，但必须保留至少一个真实硬件输入。

## 已知技术风险

- ROROLEE App 与现场 Agent Stack 的具体联通状态需现场确认。
- Agent_link 的 Wi-Fi 后端不可作为基线。
- C 板为已经领取的唯一目标板；现成 Agent_link 只覆盖摄像头、ST7789 和 WS2812，PIR/测距/按键等需补适配。
- C 板摄像头占用 GPIO4–18 中的大量引脚，与多种模块的默认示例引脚冲突；必须按工作模式分阶段启用。
- 图片理解、ASR、Scheduler 和长期记忆以现场部署为准。
- 连续视频应降级为单张快照或手机/电脑侧处理。
- Turn 流中断后先查状态，禁止盲目重试造成重复副作用。

## 完成定义

只有同时满足以下条件，功能才算完成：

- 使用真实设备触发。
- Agent/规则判断有脱敏证据。
- 设备或用户获得可观察结果。
- 相同脚本连续演示三次成功。
- 断网、ASR 或设备失败时有明确降级。
- README 能让拥有相同硬件的人复现最短路径。
